Fingerprint Service

Standalone fingerprint enrollment and identification service built on ASP.NET Core (.NET 8) with SourceAFIS as the recognition engine and MySQL (fingerprint_db) as the biometric template store.

It is an independent service. It owns its own API contract, configuration, and database. It does not store or access application data (names, employee codes, classes, attendance). Application data lives in the application server's own database (application_db) and is linked to the fingerprint service only through the string externalUserId.

1. Database ownership

MySQL Server
├── application_db    owned by Express / Application Server
│   └── users, classes, schedules, attendance, ...
│
└── fingerprint_db    owned by THIS service
    ├── fingerprint_subjects    (external_user_id -> application user id)
    └── fingerprint_templates   (serialized SourceAFIS template)
  • The service only ever queries fingerprint_db.
  • No cross-database foreign key exists between application_db and fingerprint_db.
  • The service never stores name, employee_code, class, schedule, or attendance.

Layers: Controllers (API) → Application (use cases) → Recognition (SourceAFIS) / Imaging (R503) → Data (repository) → fingerprint_db. Plus Diagnostics, Configuration, Errors, Health, Middleware.

3. Fingerprint pipeline (unchanged)

R503 packed image 18,432 bytes
  -> nibble unpack -> 192x192 grayscale 36,864 bytes (nibble * 17)
  -> FingerprintImage(192,192,Dpi)
  -> FingerprintTemplate.ToByteArray()
  -> LONGBLOB

Protocol constants: width 192, height 192, 36,864 pixels, 18,432 packed bytes, nibble * 17. The serialized template format is unchanged, so existing templates in fingerprint_db remain readable. Templates are never regenerated by this service.

4. API

All user references are externalUserId (a string). The service never accepts or returns name/employee code.

Not matched (normal business result, HTTP 200):

The service deliberately does not return name/employeeCode. The application server resolves externalUserId against application_db.

Errors use { "success": false, "error": { "code": "...", "message": "..." } }.

5. Enrollment

  1. Receive externalUserId (+ template or raw R503 image).
  2. Validate externalUserId non-empty, ≤ 100 chars.
  3. Obtain a SourceAFIS template (generate from raw image, or decode Base64).
  4. Atomically ensure fingerprint_subjects exists and insert the template.
  5. Return subjectId, fingerprintId, externalUserId, templateSize.

Re-enrolling the same externalUserId adds another template to the same subject (a subject may have multiple templates).

6. Identification

  1. Validate R503 size (exactly 18,432 bytes).
  2. Build the probe template.
  3. Load all candidates from fingerprint_subjects + fingerprint_templates.
  4. Score each, keep the highest, apply Fingerprint:MatchThreshold.
  5. Return externalUserId + fingerprintId when matched.

No enrolled subjects → matched:false, candidateCount:0, reason:"NO_ENROLLED_TEMPLATES". No global in-memory state; requests are independent.

7. Configuration

appsettings.json (no secrets):

{
  "ConnectionStrings": { "MySql": "" },
  "Fingerprint": {
    "Dpi": 508,
    "MatchThreshold": 40,
    "Diagnostics": { "SavePgm": false, "Directory": "./diagnostic-captures" }
  },
  "Server": { "MaxRequestBodySizeBytes": 65536 },
  "Cors": { "AllowedOrigins": [] },
  "Urls": "http://0.0.0.0:5001"
}

The connection string must point to fingerprint_db and use a fingerprint_user with access only to that database:

ConnectionStrings__MySql=Server=...;Port=3306;Database=fingerprint_db;User ID=fingerprint_user;Password=...;

Do not use the application server's connection string or database user.

8. Security, logging, diagnostics, reliability

  • Centralized error contract; no stack traces/SQL/paths exposed.
  • Request body limits, content-type + exact-size validation.
  • CORS disabled unless Cors:AllowedOrigins is set.
  • Structured logs with X-Request-Id; no biometric data, templates, or secrets logged.
  • Diagnostic .pgm writing is off by default and must remain off in production. Never commit .pgm files.
  • Async DB access with CancellationToken; graceful shutdown (30s).
  • Auth/TLS are not implemented here and must be added at the reverse proxy or as a configurable scheme before public exposure.
  • Threshold/DPI are development defaults and must be calibrated.

9. Testing

dotnet test ../FingerprintService.sln

Unit + integration tests cover R503 decoding/validation, threshold evaluation, enrollment/identification logic, health, error contracts, and architecture guard tests that fail if cross-database coupling is reintroduced (Express must not query fingerprint tables; the fingerprint service must not query application data).

10. Breaking changes vs. the shared-database version

  • Enrollment now uses externalUserId; name/employeeCode are not stored.
  • Identification returns externalUserId + fingerprintId instead of userId/name/employeeCode.
  • The service no longer reads a users table; it uses fingerprint_subjects + fingerprint_templates in fingerprint_db.
  • Legacy /enrollment still accepts the old JSON shape but bridges employeeCode → externalUserId and ignores name.

        │
        ▼
Fingerprint Service (:8080 in Docker)
        │
        ▼

Docker:

docker build -t fingerprint-service ./fingerprint-service
docker run --rm -p 8080:8080 \
  -e ConnectionStrings__MySql="Server=mysql;Port=3306;Database=fingerprint_db;User ID=fingerprint_user;Password=...;" \
  fingerprint-service

Because the service is decoupled, it can be moved to a separate server with only its own connection string changed.
